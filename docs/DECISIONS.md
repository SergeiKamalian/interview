## 2026-06-12 — Хранить документацию внутри репозитория

### Решение

Вся проектная документация хранится внутри папки `docs/`.

Основные файлы:

- `docs/PROJECT.md`;
- `docs/DECISIONS.md`;
- `docs/tasks/`.

### Причина

Проект будет развиваться через Cursor, поэтому важно, чтобы контекст проекта был прямо в репозитории.

Cursor должен видеть:

- смысл проекта;
- принятые решения;
- текущие задачи;
- выполненные задачи;
- будущий план.

### Последствия

Чат используется для обсуждения и планирования, но постоянная память проекта хранится в репозитории.

### Решение

Проект хранится в одной общей директории, но frontend и backend находятся отдельно:


## 2026-06-12 — Использовать SQL migrations без Prisma

### Решение

Миграции делаем через SQL-файлы и собственный migration runner.

Используем таблицу `schema_migrations`.

### Причина

Такой подход ближе к `captcha-back`.

Он даёт полный контроль над SQL-схемой и не привязывает проект к ORM.

### Последствия

Нужно будет реализовать:

- папку `backend/migrations`;
- migration runner;
- таблицу `schema_migrations`;
- проверку уже применённых миграций;
- запуск миграций через отдельный `migrate` service в Docker Compose.

## 2026-06-12 — Использовать GraphQL как основной бизнес API

### Решение

Основной бизнес API backend будет через GraphQL.

GraphQL используется для:

- interviews;
- candidates;
- attempts;
- messages;
- evaluations;
- question bank;
- analytics;
- dashboard data.

### Причина

В проекте много связанных данных.

Например, для страницы отчёта кандидата нужно получить:

- кандидата;
- интервью;
- попытку;
- сообщения;
- transcript;
- оценки по вопросам;
- checkpoint results;
- финальную оценку;
- audio/video ссылки.

Через GraphQL frontend сможет запросить ровно те данные, которые нужны конкретной странице.

### Последствия

В backend нужно будет настроить GraphQL module, schema, resolvers, input types и guards.

REST не будет основным способом бизнес-коммуникации.

## 2026-06-12 — Оставить REST для файлов и технических endpoints

### Решение

REST endpoints используются только для:

- health check;
- file upload;
- file download;
- webhooks;
- технических internal endpoints.

### Причина

Audio/video файлы неудобно передавать через GraphQL.

Для загрузки больших файлов лучше использовать REST endpoint или presigned upload URLs.

### Последствия

Backend будет иметь смешанный подход:

- GraphQL для бизнес-логики;
- REST для файлов, health, webhooks и технических endpoints.

## 2026-06-12 — AI не является источником правды

### Решение

AI не должен самостоятельно придумывать правильные ответы и критерии оценки.

Источник правды — наша база вопросов, эталонных ответов и checkpoint-критериев.

### Причина

Если AI сам придумывает оценку, результат может быть неточным, мягким или слишком субъективным.

Нам нужна строгая проверка ответа кандидата по заранее подготовленной базе.

### Последствия

Каждый вопрос должен иметь:

- профессию;
- стек;
- уровень;
- тему;
- текст вопроса;
- эталонный ответ;
- checkpoint-критерии;
- веса критериев;
- максимальный score;
- примеры хороших и плохих ответов.

AI используется как инструмент сравнения ответа кандидата с этими критериями.

## 2026-06-12 — Делить задачи по отдельным файлам

### Решение

Задачи проекта хранятся не в одном большом `TASKS.md`, а разделяются по отдельным файлам внутри `docs/tasks/`.

Структура:

```txt
docs/tasks/
  README.md
  00-project-setup.md
  01-backend-foundation.md
  02-frontend-foundation.md
  03-auth-company.md
  04-question-bank.md
  05-interview-core.md
  06-ai-evaluation.md
  07-dashboard-analytics.md
  08-voice-video.md
  09-ats-integrations.md
  10-deployment.md
```

### Причина

Один большой файл задач быстро станет неудобным.

Разделение по файлам помогает:

- быстрее находить нужную часть проекта;
- давать Cursor конкретный контекст;
- не смешивать frontend, backend, AI и аналитику;
- понимать, что уже сделано, а что ещё нет.

### Последствия

Каждый task-файл отвечает за свою часть проекта.

После выполнения задачи нужно обновлять соответствующий task-файл.
