# AI Interviewer Platform

## 1. Идея проекта

AI Interviewer Platform — это платформа для компаний, которым нужно быстро проводить первичный технический отбор большого количества кандидатов.

Компания создаёт техническое интервью, получает публичную ссылку, отправляет её кандидатам, а кандидаты проходят AI-интервью.

После прохождения интервью компания получает:

- оценку кандидата;
- transcript интервью;
- запись голоса;
- запись видеоинтервью;
- краткое summary;
- сильные стороны;
- слабые стороны;
- риски;
- рекомендацию по найму;
- детализацию оценки по каждому вопросу;
- аналитику по темам и навыкам;
- shortlist лучших кандидатов.

Продукт не заменяет финальное живое интервью.

Главная цель продукта — автоматизировать первый этап технического скрининга и помочь компании быстро понять, кого из большого потока кандидатов стоит приглашать дальше.

---

## 2. Главная проблема

Компании часто получают много откликов на одну вакансию.

Пример:

Компания ищет Frontend React Developer и получает 500 откликов.

Проблемы:

- HR не всегда может глубоко оценить технические навыки.
- У техлидов нет времени интервьюировать всех.
- Резюме могут выглядеть хорошо, но не отражать реальные знания.
- Хорошие кандидаты могут потеряться среди большого потока.
- Ручной скрининг занимает слишком много времени.
- Интервью часто проходят не по единому стандарту.
- Кандидаты могут красиво говорить, но не закрывать важные технические критерии.
- AI без строгой базы знаний может оценивать слишком мягко, неточно или “по впечатлению”.

Платформа решает это тем, что автоматически проводит первый технический скрининг, но делает это не хаотично, а по заранее подготовленной базе вопросов, эталонных ответов и критериев оценки.

## 3. Целевая аудитория

### Компании

Компании, которые нанимают разработчиков и получают много заявок.

Примеры:

- стартапы;
- аутсорс-компании;
- продуктовые компании;
- рекрутинговые агентства;
- HR-команды;
- технические команды.

### HR / Рекрутеры

Рекрутеры, которым нужно отфильтровать кандидатов перед передачей техлиду.

### Tech Leads

Техлиды, которые хотят экономить время и проводить живые интервью только с теми кандидатами, которые уже прошли базовую техническую проверку.

### Candidates

Кандидаты, которые получают публичную ссылку и проходят интервью онлайн.

## 4. Главная ценность продукта

Главная ценность продукта:

```txt
Не заменить человека, а быстро и честно отфильтровать большой поток кандидатов.
```

Компания вместо 500 сырых откликов получает структурированный список кандидатов:

- кто прошёл интервью;
- кто не прошёл;
- у кого высокий score;
- кто слабый;
- кто подходит под вакансию;
- какие темы кандидат знает хорошо;
- какие темы кандидат провалил;
- где кандидат ответил неполно;
- где кандидат ошибся;
- кого стоит пригласить на живое интервью.

## 6. Что НЕ входит в первый MVP

Первый MVP всё равно не должен превращаться в бесконечного монстра.

Пока не делаем:

- платежи;
- Stripe-интеграцию;
- сложную систему тарифов;
- роли внутри команды;
- enterprise SSO;
- мобильное приложение;
- календарные интеграции;
- email-автоматизацию;
- сложный античит уровня proctoring;
- marketplace вопросов;
- публичную библиотеку вопросов для всех пользователей.

Эти функции можно добавить позже, когда основной flow уже будет работать.

## 7. База вопросов и эталонных ответов

Одна из самых важных частей продукта — собственная база вопросов, эталонных ответов и критериев оценки.

AI не должен полностью самостоятельно придумывать вопросы, правильные ответы и критерии оценки.

Главный источник правды — наша база знаний.

Для каждого вопроса в базе должны храниться:

- профессия;
- стек;
- уровень кандидата;
- тема;
- сложность;
- текст вопроса;
- краткий правильный ответ;
- полный эталонный ответ;
- список обязательных checkpoint-критериев;
- вес каждого checkpoint;
- максимальный score;
- примеры хороших ответов;
- примеры плохих ответов;
- подсказки для внутренней оценки;
- список типичных ошибок кандидатов.

Оценка кандидата должна строиться не на общем впечатлении AI, а на сравнении ответа кандидата с checkpoint-критериями из базы.

AI должен использовать базу знаний как источник правды.

## 8. Принцип оценки по checkpoint-критериям

Каждый вопрос должен быть разбит на конкретные критерии.

Пример вопроса:

```txt
Что такое useEffect в React?
```

Пример checkpoint-критериев:

- кандидат понимает, что `useEffect` используется для побочных эффектов;
- кандидат понимает `dependency array`;
- кандидат понимает, когда эффект запускается;
- кандидат знает про `cleanup function`;
- кандидат может привести практический пример использования;
- кандидат не путает `useEffect` с обычной функцией рендера;
- кандидат понимает риски неправильных зависимостей.

Если вопрос оценивается максимум в 5 баллов, то каждый checkpoint может иметь свой вес.

Пример:

```json
{
  "question": "Что такое useEffect в React?",
  "maxScore": 5,
  "checkpoints": [
    {
      "key": "side_effects",
      "title": "Понимает назначение useEffect",
      "expected": "Кандидат объясняет, что useEffect используется для побочных эффектов в функциональных компонентах.",
      "score": 1
    },
    {
      "key": "dependency_array",
      "title": "Понимает dependency array",
      "expected": "Кандидат объясняет, что массив зависимостей контролирует повторный запуск эффекта.",
      "score": 1
    },
    {
      "key": "run_timing",
      "title": "Понимает момент запуска эффекта",
      "expected": "Кандидат говорит, что эффект запускается после рендера и при изменении зависимостей.",
      "score": 1
    },
    {
      "key": "cleanup",
      "title": "Знает про cleanup function",
      "expected": "Кандидат упоминает очистку подписок, таймеров, listeners или других ресурсов.",
      "score": 1
    },
    {
      "key": "example",
      "title": "Может привести пример",
      "expected": "Кандидат приводит практический пример: запрос данных, подписка, таймер, работа с DOM/API.",
      "score": 1
    }
  ]
}
```

Если кандидат закрыл 3 из 5 критериев, он получает примерно 3/5 за этот вопрос.

AI не должен ставить 5/5 только потому, что ответ звучит уверенно.

## 9. Как AI должен оценивать ответ

AI получает:

- вопрос;
- эталонный ответ;
- список checkpoint-критериев;
- ответ кандидата;
- уровень кандидата;
- язык интервью;
- профессию;
- стек;
- ожидаемую глубину ответа.

AI должен:

- сравнить ответ кандидата с каждым checkpoint;
- отметить, какие критерии закрыты;
- отметить, какие критерии пропущены;
- отметить, где кандидат ошибся;
- отметить, где ответ был слишком общий;
- посчитать score по весам;
- дать короткое объяснение оценки;
- дать рекомендации;
- вернуть структурированный JSON.

AI не должен:

- придумывать новые критерии оценки;
- менять максимальный score;
- оценивать только по общему впечатлению;
- добавлять баллы за красивую, но пустую речь;
- засчитывать критерий, если кандидат не сказал его явно или по смыслу;
- игнорировать эталонный ответ;
- спорить с базой знаний;
- фантазировать.

Пример результата оценки:

```json
{
  "score": 3,
  "maxScore": 5,
  "matchedCheckpoints": [
    "side_effects",
    "dependency_array",
    "run_timing"
  ],
  "missedCheckpoints": [
    "cleanup",
    "example"
  ],
  "wrongStatements": [],
  "shortSummary": "Кандидат понимает базовое назначение useEffect и dependency array, но не упомянул cleanup function и не привёл практический пример.",
  "review": "Ответ частично правильный. Для более полного ответа нужно было объяснить очистку эффекта и привести практический пример использования."
}
```

## 10. Основной flow продукта

### Flow компании

1. Пользователь компании регистрируется.
2. Пользователь входит в аккаунт.
3. Открывает dashboard.
4. Создаёт новое интервью.
5. Заполняет:
   - название вакансии;
   - роль;
   - профессию;
   - стек;
   - уровень кандидата;
   - язык интервью;
   - количество вопросов;
   - описание вакансии.
6. Система предлагает вопросы из базы знаний.
7. Пользователь может выбрать вопросы вручную или использовать автоподбор.
8. Система генерирует публичную ссылку.
9. Компания отправляет ссылку кандидатам.
10. Кандидаты проходят интервью.
11. Компания видит результаты в dashboard.
12. Компания открывает отчёт кандидата.
13. Компания смотрит score, transcript, audio/video, аналитику и рекомендации.
14. Компания решает, кого приглашать на следующий этап.
15. Компания может экспортировать результат или отправить его в ATS.

### Flow кандидата

1. Кандидат открывает публичную ссылку.
2. Видит информацию об интервью.
3. Вводит:
   - имя и фамилию;
   - email;
   - телефон, опционально;
   - LinkedIn, опционально;
   - GitHub, опционально.
4. Даёт разрешение на микрофон.
5. Даёт разрешение на камеру, если видеоинтервью включено.
6. Начинает интервью.
7. AI задаёт один вопрос за раз.
8. Вопрос может быть показан текстом и/или озвучен голосом.
9. Кандидат отвечает голосом или текстом.
10. Если включено видеоинтервью, система записывает видео.
11. Ответ кандидата превращается в transcript.
12. AI оценивает ответ по checkpoint-критериям.
13. AI задаёт следующий вопрос или уточнение.
14. Интервью завершается после нужного количества вопросов.
15. Система генерирует финальную оценку.
16. Кандидат видит экран завершения.

## 13. Финальная оценка кандидата

Финальная оценка должна строиться на основе:

- оценок по вопросам;
- закрытых checkpoint-критериев;
- пропущенных checkpoint-критериев;
- ошибок кандидата;
- уровня сложности вопросов;
- соответствия ожидаемому уровню;
- поведения кандидата на уточняющих вопросах;
- уверенности ответа;
- полноты ответа.

Финальный отчёт должен содержать:

- общий score;
- категорию кандидата;
- рекомендацию по найму;
- краткое summary;
- подробное summary;
- сильные стороны;
- слабые стороны;
- риски;
- список тем, где кандидат силён;
- список тем, где кандидат слабый;
- список вопросов и оценок;
- список checkpoint-результатов;
- transcript;
- audio recording;
- video recording.

## 14. Score и категории

### Score

Основная шкала:

```txt
0–10
```

Пример:

- 0–1 — очень слабый кандидат;
- 2–4 — слабый / basic;
- 5–6 — средний;
- 7–8 — хороший;
- 9–10 — сильный.

### Категории

```txt
weak
basic
average
good
strong
```

### Hire Recommendation

```txt
strong_reject
reject
maybe
invite
strong_invite
```

Рекомендация не должна быть абсолютным решением.

Это подсказка для компании, а не финальное решение о найме.

## 15. Голосовой режим

В MVP должен быть голосовой режим.

Голосовой режим нужен, чтобы интервью было ближе к реальному разговору и чтобы кандидат не просто копировал текстовые ответы.

Функции:

- кандидат даёт доступ к микрофону;
- AI задаёт вопрос голосом;
- кандидат отвечает голосом;
- система записывает аудио;
- speech-to-text превращает ответ в текст;
- transcript сохраняется;
- AI оценивает transcript по базе знаний;
- audio recording сохраняется и доступен компании.

Важно:

Оценка должна строиться по transcript и checkpoint-критериям, а не просто по голосу или уверенности кандидата.

---

## 16. Видеоинтервью

В MVP должно быть видеоинтервью.

Функции:

- кандидат даёт доступ к камере;
- система записывает видео во время интервью;
- видео сохраняется;
- компания может посмотреть запись;
- видео связывается с конкретной попыткой интервью.

На первом этапе видео используется как запись интервью для review.

Сложный proctoring и античит по видео пока не входят в MVP.

---

## 17. ATS-интеграции

В MVP должны быть базовые ATS-интеграции или минимум подготовленная архитектура для них.

Цель ATS-интеграции:

- отправлять результаты кандидата во внешнюю систему;
- синхронизировать кандидатов;
- экспортировать score, summary и recommendation;
- не заставлять HR вручную переносить данные.

Минимальный MVP-вариант:

- webhook после завершения интервью;

## 18. Продвинутая аналитика

В MVP должна быть продвинутая аналитика для компании.

Аналитика должна показывать не только общий score, но и картину по кандидатам и навыкам.

Минимальная аналитика:

- всего кандидатов;
- сколько начали интервью;
- сколько завершили интервью;
- completion rate;
- средний score;
- median score;
- лучшие кандидаты;
- слабые кандидаты;
- распределение по категориям;
- средний score по вопросам;
- средний score по темам;
- средний score по навыкам;
- какие темы чаще всего проваливают;
- какие темы кандидаты знают лучше;
- сравнение кандидатов между собой;
- воронка кандидатов;
- расходы AI по интервью;
- расходы AI по компании.

Пример:

```txt
React Hooks: average score 6.8/10
TypeScript: average score 4.2/10
CSS: average score 7.1/10
Architecture: average score 5.5/10
```

Frontend использует RTK Query как основной слой работы с сервером.

REST-запросы допускаются только для:

- upload/download файлов;
- health checks;
- технических endpoints.

Основной подход:

- backend предоставляет GraphQL API;
- frontend отправляет GraphQL queries и mutations;
- RTK Query управляет кешированием, loading/error состояниями и invalidation;
- GraphQL documents хранятся рядом с features/entities;
- типы GraphQL должны быть по возможности сгенерированы автоматически.

## 22. Главный принцип разработки

Не строить всё хаотично.

Да, MVP получается большим, потому что в него входят:

- база знаний;
- голос;
- видео;
- ATS;
- аналитика.

Но разработку всё равно нужно делать по порядку.

Правильный порядок:

1. Сначала база проекта и документация.
2. Потом backend foundation.
3. Потом frontend foundation.
4. Потом база вопросов и эталонных ответов.
5. Потом создание интервью.
6. Потом кандидатский flow.
7. Потом текстовая версия интервью.
8. Потом AI-оценка строго по checkpoint-критериям.
9. Потом dashboard и отчёты.
10. Потом голосовой режим.
11. Потом видеоинтервью.
12. Потом аналитика.
13. Потом ATS-интеграции.

Главное правило:

```txt
AI не является источником правды.
Источник правды — наша база вопросов, эталонных ответов и checkpoint-критериев.
```

AI используется как инструмент сравнения ответа кандидата с нашей базой, а не как свободный фантазёр.
